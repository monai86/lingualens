## 1. Executive Summary & Architectural Classifications

This document establishes the verified capability mapping between the canonical FastAPI Assessment V2 backend endpoints (48 registered routes under `/api/v2`), the web client (`assessment-v2-client.ts`), the shared Python client (`packages/tui/client.py`), and the desktop consumers (Tkinter GUI `packages/gui/app.py` and Terminal TUI `packages/tui/workflow.py`).

### Strict Classification Taxonomies

To prevent misleading claims of readiness, every capability across the 7 clinical workflow stages is classified under one of the following exact categories:

1. **Full Parity Verified**: Backend endpoint, client methods, and consumer UI surfaces (GUI and TUI) are fully integrated, with automated tests validating end-to-end behavior against canonical schemas and state isolation.
2. **Client Implemented, Consumer Pending**: Backend endpoint and client methods exist and are tested at the transport layer, but desktop GUI/TUI consumer interfaces have **not yet integrated** the calls (e.g. GUI/TUI still invokes legacy v1 methods). *Client-only implementation does NOT constitute GUI/TUI parity.*
3. **Backend Present, Client Unmapped**: Backend endpoint and service exist with complete schema/route definitions in `apps/api/`, but the shared Python client (`packages/tui/client.py`) lacks the corresponding methods.
4. **Derived Client Behavior**: A client-side helper method derived from canonical endpoints (e.g., `get_active_consent()` filtering `GET /children/{id}/consents` by status and version). *No synthetic backend endpoint exists or may be created for derived behavior.*
5. **Backend Capability Absent**: Feature or workflow conceptualized in domain/research models (e.g., raw observations or instrument forms) that does not currently expose HTTP REST routes in `apps/api/app/assessment_v2/routes.py`.
